# BingX separate positions and linked TP/SL: research and migration plan

Research date: 27 October 2026. This is an implementation plan, not a claim that separate-position mode or API-linked brackets have been tested. No account settings were changed and no live or test orders were sent for this research. The current shared-position admission and recovery policy is described in [Live parent admission isolation](live-parent-isolation.md).

## What the official sources say

- [BingX Separate Isolated guide](https://bingx.com/en/support/articles/11676733405711): ordinary Cross and Isolated aggregate orders for the same pair and direction. Separate Isolated provides individually managed positions for multiple same-direction orders and assigns margin per position. The feature requires Single-Asset and Hedge modes; availability was being rolled out by region.
- [Swap trade API reference](https://github.com/BingX-API/api-ai-skills/blob/main/skills/swap-trade/api-reference.md): `POST /openApi/swap/v2/trade/marginType` lists `SEPARATE_ISOLATED`; closing in that mode requires `positionId`. `POST /openApi/swap/v1/trade/closePosition` closes the named position at market and returns an order ID and position ID. The reference's `GET` margin-type response lists only `ISOLATED` and `CROSSED`, so the documented readback for Separate Isolated remains unclear. Position mode is separately queryable through `GET /openApi/swap/v1/positionSide/dual`.
- The trade reference and [BingX swap-trade skill reference](https://github.com/BingX-API/api-ai-skills/blob/main/skills/swap-trade/SKILL.md) describe `stopLoss` and `takeProfit` objects, serialized as JSON strings, attached to a `MARKET` or `LIMIT` entry. Their nested trigger and limit prices are JSON numbers. Attached stops support `STOP` or `STOP_MARKET`; attached targets support `TAKE_PROFIT` or `TAKE_PROFIT_MARKET`. The documentation does not list an attached trailing order type. For hedge mode it says not to send `reduceOnly`; `closePosition=true` closes the entire position on trigger, and `stopGuaranteed=true` makes the quantity field ineffective. These are material when other ownership is pooled into a position.
- [BingX TP/SL upgrade guide](https://bingx.com/en/support/articles/15074354955791), dated 3 February 2026, describes partial-position TP/SL groups: if both are set, after one is triggered and executed the other is canceled. When TP and SL are set together during order creation, their amounts are managed together on adjustment. It says separately setting or adjusting TP or SL while holding a position does not automatically synchronize their amounts. The upgrade was being rolled out in phases.
- The trade reference documents a quantity `amend` for an open order and an atomic `cancelReplace` for a **single** order; its batch variant executes the individual replacements independently. This does not establish atomic replacement or synchronized sizing of a TP/SL pair.

## Important unknowns

The support article describes a user-facing feature; the API reference does not explicitly establish that attaching both JSON objects produces the same linked cancellation and amount-update behavior in every account, nor how that link is represented, queried, edited or recovered after restart. It does not specify exactly what happens after a **partial** execution. We found no documented public API endpoint that converts the existing separately submitted CTS V/Y orders for an already-held position into a linked pair. These are unknowns, not proof that BingX lacks the behavior.

The documented entry response provides an order ID but no `positionId`. The [account positions reference](https://github.com/BingX-API/api-ai-skills/blob/main/skills/swap-account/api-reference.md) provides `positionId` but does not document an entry-order-to-position association. The [account WebSocket reference](https://github.com/BingX-API/api-ai-skills/blob/main/skills/swap-ws-account/api-reference.md) documents optional TP/SL parent-order field `o.li`, not a position ID. Without a verified authoritative mapping, a timestamp, pair, side, price or quantity match cannot prove ownership when orders or external activity overlap. Preserve IDs as exact strings; a large numeric order or position ID must never pass through a lossy JavaScript number.

The API reference currently calls the request parameter `clientOrderId` and says it is supported for `MARKET` and `LIMIT` only. CTS currently sends `clientOrderID` and uses client IDs to identify conditional exits. A [historical BingX repository issue](https://github.com/BingX-API/BingX-swap-api-doc/issues/26) shows the older spelling in examples and messages. The swap-trade skill reference specifies alphanumeric-only IDs, whereas CTS tags contain an underscore and [earlier project VST notes](live-vst-full.md) report orders with underscored tags. The accepted casing, format and conditional-order ID round trip are therefore unresolved documentation/behavior questions; neither this research nor mocked tests establishes which work in the intended venue environment. Do not blindly change IDs on existing orders or assume native IDs survive submission and restart.

Freezing software reconciliation cannot stop an oversized legacy conditional already resting on the exchange from triggering against pooled same-side quantity. Nor do bounded quantities or locally independent strategy lanes prove that two independently submitted native exits are exchange-linked OCO. An operator adding a same-side position after admission, venue gaps, partial fills, rejected orders and network loss remain risks. The one-parent admission guard is a conservative restriction on new CTS exposure, not retroactive isolation or a fill guarantee.

## Work required for a structural solution

1. Obtain an authoritative, restart-recoverable entry-order-to-position association and a trustworthy way to verify Separate Isolated is active. Until then, do not bind an ambiguous position to a lane or enable concurrent same-side parents on the assumption that it is safe. Make any future mode support explicit and opt-in; do not switch an active account automatically. Preserve existing shared positions and their protective orders for reconciliation rather than inventing a per-parent split.
2. Extend `BookPosition` and `BookOrder` in `src/core/exchange/bingx.server.ts` to retain verified position and order associations, add Separate Isolated capability/readback with an explicit unknown state, and preserve exact IDs. No symbol-and-side aggregation may erase individual positions. `setMarginMode` and `parseMarginType` currently handle only Cross and ordinary Isolated.
3. Extend persistent lane, order, fill and pending-execution records with an exact `(connection, positionId)` ownership binding and verified entry/order associations. `live_orders`, `live_fills`, `live_lane_trades`, `liveLaneOpen` and `laneOrders` do not currently provide that complete binding. Model a logical parent as a set of physical position IDs where it comprises several DCA, Axis or Block orders; verify how the venue groups partial fills of each order instead of assuming one physical position per fill.
4. Rewrite `ControlTarget`, `controlTargets`, `planControl`, `ownLedger`, and live close, stop, target, trailing and cleanup paths to reconcile the owned position IDs individually. Scope every close and native protection mutation to verified identities; never apply a shared symbol-side backstop or resize across separate positions. Persist the intent before dispatch and reconcile the original venue ID after unknown outcomes instead of retrying blindly. Keep emergency protective actions available under storage failure while surfacing their possible non-durable/unknown outcome.
5. Reconcile exact fills, cumulative quantities, execution-weighted prices, fee asset and unknown fees without fabricating per-lane funding. Keep unbound, conflicting, missing or delayed evidence unresolved. An exchange-side linked bracket, if verified, must still be monitored for rejection, partial execution, sibling cancellation, unexpected changes and residual exposure. Trailing needs its own verified position-scoped design; the documented attached bracket alone does not provide it.

## Evidence required before use

Use offline tests for identity parsing and collisions, multiple physical positions per parent, interleaved same-side lanes, foreign/manual activity, stale or missing pages, partial fills, duplicate events, timeout, rejected protection, exact cleanup, and crash/restart before and after each durable checkpoint. The test must demonstrate that a fill or cancellation for one verified position cannot close or credit a different position.

After documented confirmation of account eligibility and capabilities, a controlled venue test should independently verify mode readback, entry-to-position association, MARKET and LIMIT entry responses, conditional client-ID round trips, attached-pair discovery and sibling IDs, trigger and partial-execution behavior, amount edits, cancellation/replacement, trailing, and restart recovery. The API's `/order/test` validates less than real order placement and creates no fill; success there cannot establish these execution properties. Retain receipts and unknown outcomes without exposing credentials. No such venue test was performed here, and this plan is not evidence of live profitability or guaranteed fills.
