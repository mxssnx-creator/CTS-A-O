# Entries intent identity and restart continuity

Entries identifies a submitted intent by configuration, venue symbol, bar time **and direction**. In hedge mode, a long and a short from the same configuration on the same bar have different identities and can each receive their own entry and protective orders, subject to the physical-side admission and other live gates. One-way mode still cannot hold opposite positions simultaneously. Invalid directions are rejected. This identity change does not claim that separate TP/SL orders are atomic; see [Live parent admission isolation](live-parent-isolation.md).

The per-connection `entriesPendingExecutions|<connection>` durable state carries a submitted-bar watermark for each configuration, symbol and direction, together with the existing unresolved execution records. It is checkpointed before an entry request is sent. A restart retains that direction's watermark after the execution reservation is resolved, so the same or an older bar is not resubmitted merely because an in-memory ledger was lost. A known local non-dispatch rolls the provisional watermark back; an unknown request outcome retains it. This is conservative if an older bar is later presented out of order. Pending and otherwise unresolved orders are kept independently of the watermark.

Legacy rows are not rewritten. When the old `cfg|symbol|bar` message and the row's stored direction agree, the watermark is migrated to that direction only. An invalid direction or a conflict with an embedded direction holds the symbol; a malformed legacy message holds its symbol, a missing configuration holds its symbol, and a missing symbol holds new Entries admissions globally. A direct planner caller that supplies an unqualified old key also deduplicates both directions because it does not supply a row direction.

Watermark storage grows with the number of distinct configurations, symbols and directions, rather than with every submitted order. There is no proven fixed bound on user-created configuration identities, and no silent time-based deletion. A future compaction scheme needs a durable guarantee that removed identities cannot reappear, while keeping unknown and pending executions intact.

**Legacy limitation:** older Entries versions could label an unresolved partial or cancel-pending order as `ok` or `error`. A historical row's direction and message can establish a dedupe identity, but its old status alone does not prove its venue order is terminal. If the corresponding pending reservation and authoritative venue evidence are missing, this migration does not reconstruct that order, resolve its fills, or guarantee that another configuration on the same side is safe. Such legacy exposures need explicit venue reconciliation. A state-only restart also cannot reconstruct historical ledger rows that were already lost before these watermarks were introduced. File write/rename and the existing append journal do not establish survival of sudden power loss without storage synchronization.
